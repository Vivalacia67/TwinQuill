# TwinQuill：Krkr 直接集成路线图

更新日期：2026-10-02。适用分支：`refactor/krkr-direct-integration`。代码基线：`6f42083`。

## 目标与范围

TwinQuill 在一个应用内融合 ONScripter 与 Kirikiri/Kirikiri Z 的运行能力：导入游戏目录，识别游戏类型，调用对应的内置引擎，运行游戏，并管理游戏及其存档。

ONS 融合已完成，按用户确认作为本分支的现有基线。本分支继续将 Krkr 的开源运行时直接编译、接入 TwinQuill，沿用 `:ons` / `:krkr` 私有进程和统一启动协议。后续修改公共代码时必须保持 ONS 的启动、输入、媒体、退出及既有存档行为。

本路线图根据当前代码制定剩余步骤，首次统一 M2–M8 的范围与验收标准；保留已经验收的 M0、M1 定义，以及既有文档中 M3 对 XP3 的定位。历史“Task 3”指 M1，新任务使用 `M2.1` 等编号。阶段按能力和验收推进，不给尚未评估的工作承诺日期。

本分支完成标准：所选标准 Krkr/KAG 游戏能够在 TwinQuill 内完成启动、显示、交互、媒体播放、存档和读档；ONS 与 Krkr 能按游戏类型正确路由；游戏及存档管理可用；支持范围、失败原因和验证环境有记录。具体兼容游戏与格式以验收矩阵为准。

## 当前代码已完成的内容

| 能力 | 当前证据与边界 |

| ONS 接入 | `engine-ons/` 已融合；运行参数传入游戏根目录和 `--save-dir`，存档目录按游戏分配。作为持续回归基线。 |
| Krkr M0 | 源码与工具链、隔离进程、SAF 桥接、原始未保护 XP3 的根 `startup.tjs`、Cocos 图像/数学子集及 GLES 测试宿主，已验收。 |

已验收提交：M0 `6bd353b`；M1 启动入口 `001ddc6`、持久会话 `ed42b76`、后台返回修复与签收 `6f42083`。当前自动化基线为 Python 89 项、JVM 9 项、默认设备测试 21 项、Krkr 隔离测试 7 项全部通过，Debug/Release 和 APK 检查通过，lint 0 错误、7 警告。后续新增覆盖会增加测试数量。

## M2：TVP 宿主与基础显示

主要位置：`engine-krkr/src/main/cpp/`、`engine-krkr/src/main/java/`；上游参考 `vendor/kirikiroid2/src/core/base/`、`visual/`、`environ/`。

- **M2.1 接口与源码闭包审计。** 选定首批 KAG 版本和验收样例，列出其必需的 TVP 类、方法、属性、插件及依赖。以锁定的 Kirikiroid2 核心为主要实现来源，明确 krkrz 代码的使用边界；记录要增加的翻译单元和 Android 适配点。当前快照有 `KAGParser.cpp`，但没有已接入的 KAG 脚本框架，需要核实并固定框架来源、版本和许可。
- **M2.2 重整启动时序。** 当前 broker 先执行 `startup.tjs`，成功后才打开 GLES 宿主；标准脚本创建 `Window` 时需要实际 TVP 宿主。将请求验证、宿主初始化、TVP 注册和脚本启动拆开，按上游运行时需求建立时序，保留启动一次、错误返回和资源释放保证。
- **M2.3 接入基础 TVP 对象。** 接入所选基线需要的 `Window`、`Layer`、`Timer`、事件系统及相关基础类；实现尺寸、图层、透明度、图片和文字基础显示，以及触摸/键盘到游戏坐标的转换。先用松散 PNG/JPEG、已审计字体和自制 TJS 验证。
- **M2.4 调度与生命周期。** 明确脚本事件、Android UI、GL 的线程边界；接入定时事件、窗口关闭、暂停/恢复、表面与上下文重建。设计启动/回调的超时和取消机制，补足 M1 对不返回脚本无法中断的限制；退出不能无限等待工作线程。

**交付与验收：** 源码/接口清单、宿主时序说明、标准 TVP 测试场景和 `KRKR_M2_HANDOFF.md`。自制脚本通过标准 `Window/Layer` 显示图片与文字，定时器和输入产生可见效果；后台返回及 Activity 重建保持游戏状态；错误、取消、重复启动均能释放资源。彩色测试方块不能替代本阶段验收。

## M3：资源系统、XP3 与编码

主要位置：`krkr_vfs_storage.*`、`krkr_xp3.*`、`native-vfs/`、`Xp3ArchiveProbe.java`；参考上游 `StorageIntf`、`StorageImpl`、`XP3Archive`。

- **M3.1 统一 TVP 存储介质。** 将松散文件、SAF 和 XP3 纳入上游兼容的流与路径解析，支持图片、字体、脚本及媒体资源；实现子目录、搜索路径、归档成员查询及缓存。非 seekable Provider、权限撤销和大文件读取必须有明确处理。
- **M3.2 完成标准 XP3。** 从当前“仅原始根 startup”扩展到多成员、子目录、压缩索引及压缩段；实现多归档、补丁归档和松散文件的搜索顺序，并依据选定上游语义固定回归样例。同步探测器与实际加载器，避免识别通过但引擎找错归档。
- **M3.3 扩展游戏文本编码。** 保持 M1 的严格 Unicode 行为；按明确的游戏配置加入 Shift-JIS/CP932 等所选样例必需编码，同时验证中文/日文文件名、错误编码和路径规范化。
- **M3.4 提供私有写入基础。** 将 TVP 数据路径映射到已验证的每游戏私有存档目录，提供创建、写入、flush、替换和失败处理，优先保证原子更新。游戏目录保持只读；存档写入不依赖扩大游戏目录的 SAF 授权。审定 ONS 现有目录布局的兼容方案。

**交付与验收：** 存储/路径契约、归档与编码夹具、`KRKR_M3_HANDOFF.md`。同一场景从松散目录和压缩 XP3，经 SAF 均能读到相同资源；补丁覆盖顺序正确；大文件、损坏索引、解压膨胀和权限失效不会导致越界或无限资源占用；私有写入失败不破坏上一份有效数据。

本阶段覆盖标准未保护 XP3。需要专用过滤器的包单独列入 M6 的兼容评估；未知保护格式应报告不支持。

## M4：KAG 框架与最小游戏

主要位置：TVP 原生类注册、`KAGParser`、运行时脚本/资源加载和测试场景。

- **M4.1 接入完整启动链。** 引入已审计、固定版本的 KAG 脚本框架和测试资源，支持启动配置、框架初始化、宏及脚本包含。仅编译 `KAGParser.cpp` 不构成本阶段完成。
- **M4.2 打通视觉小说流程。** 支持所选基线的文字显示、等待、页面推进、背景/立绘、基础切换、选择支、标签跳转、调用/返回和内嵌 TJS。
- **M4.3 补齐框架必需接口。** 按 M2.1 清单实现实际启动所需的系统、字体、对象序列化和原生类。媒体对象即使没有播放标签，也可能在框架启动时创建；所选样例所需的基础音频对象与 PCM/WAV 播放在本阶段落实，不能用静默跳过或空实现冒充支持。更广媒体覆盖在 M6 完成。
- **M4.4 验证完整小型场景。** 制作带文字、图像、分支、基本声音和结束路径的自制 KAG 游戏，同时测试脚本错误、缺少资源和正常退出。

**交付与验收：** 受支持 KAG 接口/标签清单、可重复运行的样例及 `KRKR_M4_HANDOFF.md`。从 TwinQuill 游戏库启动，在标准 KAG 框架下完成一段含分支的小型游戏流程，后台返回保持状态，正常结束返回游戏库；同一内容支持松散资源和标准 XP3。本阶段不要求完成游戏内存读档和全部媒体格式。

## M5：Krkr 存档与读档

主要位置：TVP 数据路径、KAG 存储/恢复接口、`EngineRouter` 和运行会话管理。

- **M5.1 接入实际存档路径。** 将 KAG 的存档、系统数据、已读记录和配置写入 `filesDir/saves/<game-id>` 对应区域；明确两引擎文件组织策略，保持已有 ONS 存档兼容，避免切换引擎造成混写。
- **M5.2 保存与恢复游戏状态。** 按所选上游语义实现槽位保存、加载和所需序列化，恢复位置、变量、分支及可恢复的图层/音频状态。进程内 VM 保留不能代替落盘存档。
- **M5.3 保证持久性。** 覆盖退出重启、进程死亡、部分写入、空间不足和损坏存档；保留可恢复的有效数据，并输出可定位的错误。
- **M5.4 建立存档访问契约。** 为 M7 提供按游戏查询文件、占用空间、备份、恢复和清理的接口；游戏运行时的读写与管理操作需要协调。

**交付与验收：** 存档路径/格式说明、持久化回归与 `KRKR_M5_HANDOFF.md`。在分支前保存，退出并重新启动后读档，恢复相同位置和变量；两个 Krkr 游戏相互隔离；ONS 旧存档仍能读取；异常写入不会覆盖上一份有效存档。

## M6：媒体与常见扩展兼容

主要位置：上游 `visual/`、`sound/`、`movie/`、插件接口、CMake 和源码来源清单。

- **M6.1 固定兼容矩阵。** 根据目标游戏列出图像、音频、视频、转场和插件需求，选择源码可审计的实现与 Android 后端；未具备来源的依赖先完成快照和许可记录。
- **M6.2 完善显示与音频。** 补充目标样例需要的 TLG 等图像、混合/转场，以及 BGM、SE、语音、循环、音量和格式解码；验证暂停、恢复、音频焦点与资源释放。
- **M6.3 接入视频。** 实现所选格式的视频层/叠加、播放结束事件、跳过和所需音画同步；核实从 SAF/XP3 读取、seek、后台暂停和读档后的状态。
- **M6.4 接入明确的开源扩展。** 将目标游戏需要且具备合法源码的插件、过滤器编译进受控运行时，记录注册名称、版本和行为。保持来源政策，不引入任意外部 DLL 或未经审计的预编译库。

**交付与验收：** 格式/插件支持矩阵、自制媒体夹具和 `KRKR_M6_HANDOFF.md`。列入必需清单的图像、音频和视频在实际 KAG 场景中正确显示/播放，等待和结束回调可用，后台往返及退出后无遗留音频或媒体资源。未支持的格式/插件有明确诊断。

## M7：统一游戏及存档管理

主要位置：`launcher-app/`、`engine-api/`、两引擎的启动/结果适配层。

- **M7.1 完善游戏识别与路由。** 沿用已有检测与人工覆盖，支持 M3 的资源布局；对冲突、未知和不支持目录提供可理解的结果。设置按游戏持久化，两引擎交替运行不共享不应共享的状态。
- **M7.2 完善游戏库操作。** 增加所需的改名、配置、重复导入处理及重新授权。重新授权保留 `game.id` 和存档关联；从列表移除、删除存档和删除游戏内容必须是明确区分的操作。
- **M7.3 实现存档管理界面。** 展示游戏关联和空间占用，支持通过用户选择的 SAF 位置导出、导入和清理。备份包含引擎、游戏关联、格式版本及校验信息；恢复时校验归属、拒绝越界路径，并避免破坏当前有效存档。
- **M7.4 保护既有用户数据。** 删除后重新添加、迁移目录或恢复备份时提供明确的存档重新关联策略；保持 ONS 现有目录/数据兼容。运行中管理操作需要等待安全时机，覆盖确认与错误提示。

**交付与验收：** 双引擎管理与数据迁移说明、UI 回归及 `KRKR_M7_HANDOFF.md`。同一游戏库导入 ONS 和 Krkr 游戏，正确路由并各自存读档；备份后恢复可继续游戏；重复导入和重新授权不丢关联；移除列表项不擅自删除游戏或存档。

## M8：兼容验证与分支完成验收

- **M8.1 建立代表性游戏清单。** 覆盖 ONS 基线、标准 KAG、目标 Kirikiri/Kirikiri Z 游戏，以及压缩 XP3、不同编码、媒体和存档需求。记录游戏/框架版本、必需功能、测试资源来源与结果；商业游戏资源不提交仓库。
- **M8.2 完成端到端验收。** 逐项验证导入 → 自动路由 → 启动 → 交互/媒体 → 存档 → 退出 → 重启读档 → 备份恢复，包含两引擎交替启动和失败后的恢复。
- **M8.3 稳定性与性能。** 验证重复运行、较长场景、后台切换、表面/Activity 重建、进程死亡、权限丢失和低存储空间；记录启动耗时、内存、帧表现及存储缓存预算，修复阻塞运行和数据完整性的问题。
- **M8.4 完成发布候选与交接。** 运行公共验证门槛，核对 Release 与 Debug 行为，保留源码构建和 APK 原生库检查；生成 `KRKR_M8_HANDOFF.md`、用户使用/存档恢复说明和兼容矩阵，再按用户指示进行合并或发布。

**完成判据：** M2–M7 的必要能力已签收；代表性游戏清单中列为必需的用例通过；ONS 基线保持可用；游戏与存档管理验证通过；没有已知阻塞启动、必需游戏流程或数据完整性的缺陷。已知不支持项和未经验证的设备范围明确记录。

## 每阶段的公共门槛

1. 按 [源码政策](SOURCE_POLICY.md) 维护 `third_party/sources.toml` 与 `vendor/patches/<source-id>/`，保留上游快照校验和许可。新增 TVP/Cocos/媒体源码时显式更新源码清单、链接边界和相关回归；扩充经过审计的范围，不能禁用检查来通过构建。
2. 从根目录运行 Python 回归、仓库卫生及源码快照检查；构建 Debug/Release、运行 lint、两引擎 JVM 与默认/隔离设备测试、APK 原生库检查。命令见 [M1 交接文档](KRKR_M1_TJS_ENTRY.md#regression-coverage)，为各阶段新增行为补充有意义的覆盖。
3. 自制样例和可审计测试资源随测试保存；APK、原生二进制、设备日志及 SDK 配置保持忽略。交接记录写明提交、APK SHA-256、验证环境、用例、结果及剩余边界。
4. 按用户当前选择，阶段验收使用 `Medium_Phone`，Android 16 / API 36、x86_64 + ARM64 转译、SwiftShader、Vulkan 关闭；不把真机验收设为本轮推进前提。现有 `arm64-v8a` / `armeabi-v7a` 构建目标和最低 API 26 保留；未实际验证的 API/ABI 标为未验证，扩大支持声明前再补对应环境证据。
5. “编译成功”“自制样例通过”“指定游戏兼容”“阶段验收完成”分别记录。需要实际游戏效果或存档持久化的阶段，不能只用源码检查或进程内状态替代验收。
