# Krkr M5：存档与读档开发计划

更新日期：2026-10-04。分支：`refactor/krkr-direct-integration`。
开发基线：M4 提交 `78bb0b5392bfe386f34ee7a01d90f38861273994`。
用户已确认 M4 模拟器验收完成、无报错。本文件完成下一轮开发准备；M5 功能尚未实现。

## 目标与前置能力

让选定 KAG 游戏通过真实槽位文件保存剧情，退出或进程重启后仍能读档，恢复
剧情位置、游戏变量、图层及所选音频状态。进程内保留 VM 或 Home 返回不能替代此目标。

M4 已有完整固定 KAG3、KAGParser、图像/文字、PCM16 WAV 与生命周期调度。
M3 已有每游戏私有目录、结构序列化和单文件原子替换；当前 M4 场景配置
`readOnlyMode=true`，尚未验证 KAG 的实际存读档链。验证基线见 [M4 交接](KRKR_M4_HANDOFF.md)。

## 已核对的实现入口

| 位置 | 当前行为与开发重点 |
| --- | --- |
| `launcher-app/src/main/java/io/github/twinquill/launcher/EngineRouter.kt` | 通过持久化 `game.id` 分配 `filesDir/saves/<game-id>/`，复用现有启动协议。 |
| `engine-krkr/src/main/cpp/krkr_private_storage.*` | `System.dataPath` 对应 `tqsave://./`，落到该游戏的 `krkr/` 子目录；保持路径校验、32 MiB 写入额度和失败时中止替换。 |
| `vendor/kag3-1f3ab309/data/system/MainWindow.tjs` | `saveBookMarkToFile/loadBookMarkFromFile` 写入和读取槽位，校验 `saveDataID`；`storeFlags/restoreFlags` 组织剧情快照。 |
| 同文件的 `saveSystemVariables/loadSystemVariables` | `datasc.ksd` 保存配置、槽位元数据，`datasu.ksd` 保存系统变量；两者分别写入，当前没有多文件事务。 |
| `vendor/kirikiroid2/src/core/utils/KAGParser.cpp`、KAG `Conductor.tjs` | 已有 `store/restore`，需验证场景位置、调用栈、宏参数与调度恢复，按缺口补 Android 适配。 |
| KAG `GraphicLayer.tjs`、`MessageLayer.tjs`、`BGM.tjs`、`SE.tjs` | 核对实际恢复调用与已绑定接口；图层、文字页、选择链接及声音必须有运行证据。 |

`game.id` 决定应用目录归属，KAG 的 `saveDataID` 决定游戏存档格式归属；两者用途不同。
新增样例使用明确的 `saveDataID`，不能沿用 M4 配置的全零占位值证明跨游戏校验。

## 开发顺序与交付

### M5.1：路径、格式与系统数据

先跟踪完整框架的存读档调用链，形成 `KRKR_M5_STORAGE_CONTRACT.md`：列出
路径映射、文件名、序列化模式、变量类别、保存时机、额度及错误行为。
首批配置采用 `readOnlyMode=false`、`saveThumbnail=false`、`saveDataMode=""`。
普通槽位为 `data<num>.kdt`；编号不小于 999 的上游路径使用 `.ksd`。

用新的 M5 样例验证 `datasc.ksd`、`datasu.ksd` 的创建、更新和重启读取，覆盖
系统变量、已读记录与选定配置。保留 M4 样例及 ONS 原有父目录布局；游戏介质继续只读。
缩略图附加数据、偏移写入及加密模式另行审计，在明确实现前报告不支持。

### M5.2：完整槽位保存与恢复

建立独立的 `tests/fixtures/krkr-m5/` 和生成脚本，提供散文件与压缩 XP3 场景、
游戏内保存/读取入口及可见的剧情状态。使用真实 KAG 标签/接口驱动保存，
确认槽位已落盘后再向玩家显示成功。

按上游快照语义恢复场景、标签、调用栈、宏、游戏变量、背景/立绘和消息页；
分别记录 `f`、`sf`、`tf` 的持久化边界，避免承诺所有临时变量都能保存。
明确 KAG 可存档的检查点，验证恢复后分支链接可点击、跨文件调用可正常返回。

固定 KAG 的 BGM 存档保存资源、音量和暂停状态，读档重新开始循环播放；
它未保存采样偏移。M5 首批遵循该语义，音频精确定位仍属 M6。SE 的恢复会重播
记录的资源并设置循环，必须区分循环音与已结束的一次音效，防止读档后重复播放提示音。

### M5.3：跨进程持久性与失败恢复

验证正常退出重启、已完成保存后的进程终止、覆盖同一槽位和多槽位切换。
用测试拥有的临时目录注入部分写入、空间不足、损坏数据和错误 `saveDataID`，
验证失败写入保留上一份有效数据；读档失败不能覆盖存档或留下半恢复会话。

针对“槽位已替换、系统元数据尚未写完”的中断，制定并实现恢复策略；单文件
原子替换不能宣称整组文件事务已完成。明确有效版本保留、损坏文件处理及元数据
重建规则，并确保错误可定位、退出后仍可启动正常游戏。

### M5.4：供 M7 使用的存档访问契约

提供按游戏/引擎查询文件及空间占用的接口，落实备份、恢复、清理所需的文件集合、
归属校验、原子替换与会话协调。运行时写入与管理操作不得并发破坏同一份数据。
统一存档管理界面和用户选择的 SAF 导出/导入流程在 M7 实现。

每项完成后运行对应回归并保存独立提交；全部完成后交付 `KRKR_M5_HANDOFF.md`、
存档契约、可重复生成的样例和最终 APK 摘要，再提交用户模拟器验收。

## 模拟器验收标准

沿用 Medium_Phone、Android 16 / API 36、ARM64 转译、SwiftShader、Vulkan 关闭。
以下是验收用例要求；可直接执行的命令和样例操作在实现后的交接文档提供。

1. 在分支前保存槽位，进入另一剧情后读档，恢复原位置、变量、图像和消息页；继续选择后结果正确。
2. 正常退出、重开同一条目并读档；随后在保存完成后终止应用进程，重新启动仍可恢复。散文件与 XP3 均通过。
3. 在允许存档的跨文件调用检查点保存，重启读档后返回正确；槽位、系统变量、已读记录与配置分别复核。
4. 验证 BGM 资源、音量及暂停状态按上述上游语义恢复，Home 往返无残留音轨或重复调度。
5. 两个 Krkr 游戏的槽位相互隔离；交替运行 ONS，原有 ONS 存档仍能读取。
6. 自动化注入写入失败、损坏数据、错误归属和多文件中断；旧有效数据受保护，失败后能启动正常游戏。

使用覆盖安装和直接 instrumentation，沿用 [M4 命令](KRKR_M4_HANDOFF.md#5-自动化复核)。
故障测试只操作测试创建的存档，不清空现有应用数据、不导出私有数据库、不填满整个模拟器磁盘。
