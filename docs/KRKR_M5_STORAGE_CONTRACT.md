# Krkr M5：存档格式、恢复与管理契约

更新日期：2026-10-04。适用固定 KAG3 `1f3ab309106d210e3169bbbe0fb4e066ae463b42`
及当前 Android 宿主。资源访问沿用 [M3 契约](KRKR_M3_STORAGE_CONTRACT.md)。

## 目录和归属

`EngineRouter` 使用游戏库持久化的 `game.id` 分配 `filesDir/saves/<game-id>/`。
ONS 继续使用此父目录；Krkr 的 `System.dataPath="tqsave://./"` 只访问其 `krkr/` 子目录。
游戏介质及 SAF 授权保持只读。应用 ID 决定目录归属；游戏配置的 `saveDataID`
决定 KAG 槽位格式归属，两者不能互相替代。

| 默认文件 | 内容及保存时机 |
| --- | --- |
| `data0.kdt`、`data1.kdt` 等 | `id/core/user/history` 字典；游戏调用 `kag.saveBookMark(n)` 或 `[save]` 时写入。 |
| `datasc.ksd` | 槽位标题/时间/保护标记、文字速度、字体等配置；KAG 更新配置及槽位信息时保存。 |
| `datasu.ksd` | `sf` 系统变量及 `trail_<scenario>_<label>` 已读记录；KAG 保存系统变量及正常关闭时写入。 |
| `data999.ksd` 等 | 编号不小于 999 的上游特殊路径；本轮端到端验收针对普通两槽位。 |

前缀 `data` 可由游戏配置改变。M5 选定 `readOnlyMode=false`、`saveThumbnail=false`、
`saveDataMode=""`、`saveMacros=true`。样例启用 `autoRecordPageShowing=true`，
并验证文字速度配置在重启后保留。序列化结果为 UTF-8 TJS 结构表达式，按上游
`Scripts.evalStorage` 读回。缩略图 BMP、附加偏移、加密/压缩写入模式仍不支持。
私有文件每次读写上限 32 MiB，目录嵌套最多 16 层，拒绝遍历、归档成员及符号链接。
`.tq-<pid>-<sequence>` 为原子写入临时名，游戏不能使用。

## 剧情与音频恢复语义

带标题的 KAG 标签是存档检查点。槽位记录最近可保存的标签现场，读取后重放
该检查点的文字及选择链接；不会保证点击“保存”时任意字符位置的逐像素截图。
`f` 游戏变量随槽位恢复，`sf` 独立持久化并保持当前值，`tf` 临时变量不进入槽位。
Parser 的场景/标签、调用栈、宏，以及背景、立绘和消息层按上游快照恢复。

BGM 保存资源、音量和暂停标记；读档从资源开头重新循环播放，保留暂停状态。
SE 只记录仍有 `currentStorage` 的循环资源；已结束的一次音效不应再次播放。
本轮槽位样例验证 BGM 的 40% 音量、播放/暂停两种检查点；一次 SE 的结束语义
继续由 M4 音频回归覆盖。精确采样定位、淡入淡出、压缩音频和视频属于 M6。

## 写入失败与中断恢复

原生写入先完整写临时文件、`fsync`，再 `rename` 替换并同步父目录。替换前的
超额、部分写入或失败保留旧文件；替换后的目录同步失败不能承诺旧版本回滚。
每个槽位及 sc/su 文件分别提交，整组文件没有统一事务。

对于“槽位已提交、菜单元数据尚未提交”的进程中断，宿主在完整 KAG 启动后、
第一轮剧情调度前执行 `AndroidKagRecovery.tjs`。它从有效槽位的 `core.currentPageName`
及 `core.storeTime` 重建标题/日期，沿用 KAG 的元数据保存方法；不回滚 `sf` 或重写槽位。
仅处理私有数据路径、普通无缩略图/无编码模式的前 64 个槽位。无变化时不写文件。
缺失、语法损坏、格式 ID 不匹配或恢复失败的槽位会记录带编号的日志并保持原文件。

显式读取坏槽位或错误 ID 会产生 `SCRIPT_ERROR`，会话释放后仍可启动正常游戏。
有效的其他槽位保持原样。损坏的 sc/su 文件仍按 KAG 报错，不能凭空恢复系统变量；
应从已有有效备份恢复。M5 没有无条件自动回滚所有历史版本，也不声明断电事务保证。

## 供 M7 使用的离线访问

`KrkrSaveStore(filesDir, gameId).acquire()` 返回可关闭的 `Lease`。
在 `try-with-resources` 中使用 `list()`、`bytes()`、`snapshot()`、`restore(snapshot)`
及 `clear()`。清单路径均相对 `krkr/`，不包括锁、恢复日志及未提交的原生临时文件。
同一租约的操作串行化；关闭后拒绝继续使用。

`Snapshot` 包含游戏 ID、格式版本 1 和独立复制的文件字节。拒绝跨游戏恢复、
文件/目录冲突、越界路径、无效 Unicode、超额深度及内部临时名。
清单最多 4,096 个文件/目录节点，单文件 32 MiB，快照总计 128 MiB。
该接口使用内存文件集；M7 负责外部备份的引擎标识、校验和、版本清单及 SAF 流式传输。

租约及运行时共用父目录 `.krkr-session.lock` 的字节范围锁，配合 Java 同进程
所有权表。游戏运行期间查询/备份/清理/恢复均返回“正在使用”；反向启动同样被拒绝。
进程死亡后内核释放锁。锁文件本身保留，不通过删除锁文件解除占用。

恢复先完整写入 `.krkr-restore-<random>/` 并同步文件，原子提交恢复标记，
将旧 `krkr/` 改名为 `.krkr-previous/`，再切换新树。恢复及清理只处理 Krkr 子树。
启动或下次租约获取时：新树存在则保留新树；新树缺失且旧树存在则回滚旧树；
仅有完整暂存树时恢复该树。离线租约清除已完成标记及遗留暂存文件。
此机制针对进程中断；文件系统断电持久性仍需后续验证。ONS 父目录和其他游戏不参与替换。
